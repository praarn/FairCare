# Healthcare Cost Predictor — Implementation Documentation

This document describes what the project does, how it's built, and how every
feature works end to end. It reflects the current state of the codebase
(Phase 2 / MVP — rule-based, no ML/LLM yet).

---

## 1. What this project is

A web app that helps people in India estimate the cost of a medical
treatment, compare that cost across cities, check government health-scheme
eligibility, find hospitals (with government/empanelled options surfaced
first), and get a rough diagnosis lead from a symptom description — all
built on transparent, rule-based logic and **placeholder sample data**
(clearly labeled `"SAMPLE DATA"` in the `source` field of every record; not
real CGHS/PM-JAY figures yet).

The guiding principle throughout the backend: **no cost figure or
eligibility result is ever generated by an LLM.** Every number traces back
to a JSON "database" (`backend/app/data/*.json`), and every fallback or
approximation is explicitly labeled as such in the API response, never
silently substituted.

## 2. Tech stack

| Layer | Technology |
|---|---|
| Backend | Python, FastAPI, Pydantic v2, Uvicorn |
| Backend "database" | Flat JSON files under `backend/app/data/` (no real DB yet) |

### 3.3 Treatment search — two distinct scoring modes

Both live in `treatment_service.py` and share the same candidate pool (`name`
+ `aliases` + `name_hi`, plus `symptoms` in strict mode), but score
completely differently:

- **Lenient (`/search`, plain name search)** — blends word-overlap ratio,
  per-word `SequenceMatcher` fuzzy similarity, and whole-string similarity
  (`0.4 * overlap + 0.4 * avg_word_coverage + 0.2 * seq_ratio`). Threshold is
  low (`0.32`) and **always falls back** to the closest few results rather
  than showing nothing — appropriate because the user already knows what
  treatment they want and typos/voice-transcription noise are expected.

- **Strict (`/search-symptoms`, Symptom Checker)** — an F1-style
  precision/recall blend over exact (stopword-stripped) word matches, with
  a narrow allowance for near-exact fuzzy matches (similarity ≥ 0.82, i.e.
  typo-level only). Threshold is higher (`0.35`) and **there is no
  fallback** — an empty result correctly means "nothing matched, see a
  doctor," not an error. This prevents one incidental shared word (e.g.
  "pain") from letting an unrelated treatment surface as a false positive.

A shared stopword list (`STOPWORDS`) strips generic filler words ("pain,"
"surgery," "cost," "please," etc.) before scoring so they can't dominate the
match over a real anatomical/symptom term.

### 3.4 Cost estimation — five-tier fallback (`cost_service.py`)

`estimate_cost()` tries progressively broader data tiers, and **every**
response discloses exactly which tier produced the number via
`is_fallback` + a human-readable `fallback_reason` (bilingual, en/hi):

1. **Exact city + hospital type** — most specific match.
2. **Exact city, any hospital type** — pooled across types in that city.
3. **State-wide pool** — if no exact city match, pools all records in the
   (given or city-derived) state.
4. **National reference rate** — a real, cited PM-JAY/CGHS government
   package rate from `national_reference.json`, used only for treatments
   where genuine research found a verifiable national figure. Explicitly
   *not* pooled sample data.
5. **National pooled sample average** — last resort, honestly labeled as a
   national average of whatever sample data exists, not location-specific.

If none of the five tiers has any data at all, the API returns 404 with a
clear "no verified data for this treatment" message rather than fabricating
a number.

Each estimate also carries a **confidence score** (0–1, labeled
low/medium/high) computed from a weighted blend of sample size (`min(n/100,
1.0)`) and data recency (full weight for current-year data, decaying to
0.4 for anything ≥4 years old), and a set of **factors** explaining the
estimate in plain language (e.g. "private hospitals in this data run about
X% higher than government hospitals," "estimate is based on N pooled
records," location basis).

### 3.5 Hospital ranking (`hospital_service.py`)

- Filters hospitals by `treatment_id` (must be in `treatments_offered`),
  optionally by `city` and `type`.
- Enriches each result with a matching `cost_avg`/`cost_source` from
  `cost_records.json` when available (same treatment + city + hospital
  type).
- Two ranking modes:
  - **Default**: government-first, then by rank order
    (`govt` → `private_low` → `private_mid` → `private_high`), then by
    rating descending within each type.
  - **Budget mode** (`budget_mode=true`): pure ascending cost, with
    government hospitals as the tiebreaker for equal/missing cost.

### 3.6 Scheme eligibility (`scheme_service.py`)

Plain deterministic rule evaluation per scheme (income ceiling, state
inclusion list, government-employment/pension requirement) — intentionally
**not** an LLM call, since eligibility for a real government scheme is
legally sensitive and needs to stay auditable and unit-testable rule by
rule. Every result includes a plain-language `reason` built from which
specific rules passed/failed, plus `coverage_details`, `application_steps`,
and an `official_link` for legitimate next steps.

### 3.7 Authentication (`auth_service.py`)

- File-backed "database" (`users.json` / `sessions.json` /
  `reset_tokens.json`), matching the rest of the project's JSON-file
  approach for this MVP phase — intended to be swapped for a real DB later.
- Passwords hashed with **PBKDF2-HMAC-SHA256**, 200,000 iterations, random
  16-byte salt per user (stdlib `hashlib`/`secrets` only — no external auth
  library dependency).
- Sessions are random URL-safe tokens (`secrets.token_urlsafe(32)`), 7-day
  TTL, stored server-side.
- Password reset: 1-hour TTL token. Since no email service is configured,
  the reset token is returned directly in the API response (with an
  explicit note saying so) rather than silently pretending to email it —
  a deliberate MVP trade-off; see §6 for the known limitation this
  introduces.
- All file reads/writes explicitly use `encoding="utf-8"` throughout the
  backend, since Windows defaults to `cp1252` otherwise, which cannot
  decode the Hindi (Devanagari) content in the data files.

### 3.8 CORS

Configured in `main.py` to allow the frontend from `localhost:3000`,
`127.0.0.1:3000`, and `[::1]:3000` — covering the common case where the dev
server is opened under a different loopback hostname than the one the
backend's allowlist expects (a frequent source of a silent, unlogged
"Failed to fetch" in the browser).

### 4.2 Pages and what they do

- **Home (`/`)** — Treatment autocomplete (calls `/api/treatments/search`
  as you type), a city dropdown (7 major cities) with an "other" option
  that reveals a full state dropdown, an optional hospital-type filter,
  and a submit that routes to `/results` with the selections as query
  params.

- **Results (`/results`)** — Server component; requires `treatment_id` +
  (`city` or `state`) in the URL. Calls `/api/predict-cost` server-side,
  then renders: a cost gauge (min/typical/max), a confidence badge, an
  expandable "why this estimate" panel (factors + raw source records), a
  persistent disclaimer banner, a payment-plan/EMI estimator, an insurance
  coverage estimator, a "price check" tool, share-to-WhatsApp, read-aloud,
  and "save to history."

- **Compare (`/compare`)** — Pick one treatment, toggle multiple cities
  (from the same `CITIES` list), optional hospital-type filter, then fires
  a `predictCost` call per city in parallel and sorts results
  cheapest-first, flagging the lowest-cost city.

- **Symptom Checker (`/symptom-checker`)** — Free-text symptom description
  → `/api/treatments/search-symptoms` (strict scorer) → list of candidate
  treatments with a city selector (added so estimates reflect the user's
  actual location rather than a fixed default) → link into `/results` per
  candidate. Always shows a medical disclaimer.

- **Eligibility (`/eligibility`)** — Income input, state dropdown,
  government-employee/pensioner checkbox → `/api/schemes/eligible` → list
  of schemes with eligible/not-eligible status, plain-language reasoning,
  coverage details, application steps, and official links.

- **Hospitals (`/hospitals` and `/hospitals/[id]`)** — List view supports
  city/type filters and a "budget mode" cheapest-first toggle; each card
  shows government/empanelled status via a stamp badge. Detail view shows
  contact info, rating, empanelled schemes, and an embedded OpenStreetMap
  location.

- **History (`/history`)** — Client-side only; reads a locally-stored list
  of previously viewed estimates (no backend persistence) so a user can
  revisit past lookups without needing an account.

- **Methodology (`/methodology`)** — Static explanatory page describing
  how the cost tiers, confidence scoring, and scheme eligibility rules
  work — the human-readable counterpart to §3.4/§3.6 above.

- **Auth pages (`/login`, `/signup`, `/forgot-password`,
  `/reset-password`)** — Standard forms; signup enforces password length
  (≥8) and confirmation match client-side, plus the same rules are
  re-checked server-side. Successful login/signup sets an httpOnly-style
  cookie (`sahaj_auth_token`) and redirects home. Forgot-password shows the
  reset link directly on screen (see §3.7/§6) since no email service is
  wired up yet.

### 4.3 Auth flow (client)

- `AuthProvider` (`lib/auth-context.tsx`) exposes `login`, `signup`,
  `logout`, and the current `user`, backed by a `sahaj_auth_token` cookie
  (7-day max-age) and calls into `lib/api.ts`.
- `RootLayout` (`app/layout.tsx`) is a server component that runs on
  *every* request: it reads the cookie, and if present, server-side calls
  `/api/auth/me` to hydrate `initialUser` before the page ever renders
  client-side — avoiding an auth-flash on load.
- `proxy.ts` (the Next.js 16 successor to `middleware.ts`) runs on every
  route except static assets: public paths (`/login`, `/signup`,
  `/forgot-password`, `/reset-password`) are always allowed through;
  everything else requires the `sahaj_auth_token` cookie, redirecting to
  `/login` if it's missing.

### 4.4 Internationalization

- 8 languages: English, Hindi, Tamil, Telugu, Bengali, Marathi, Gujarati,
  Kannada (`lib/i18n.ts`).
- Language is stored in a `sahaj_lang` cookie, read server-side in
  `layout.tsx` for the initial render and available client-side via
  `useLanguage()`.
- Every user-facing string (nav labels, form labels, disclaimers, factor
  labels, share text) is looked up via `t(lang, key)`, with keys enforced
  at compile time (`TranslationKey = keyof typeof dict`) so a typo'd key
  fails the TypeScript build rather than silently rendering blank.
- Treatment names/categories additionally carry their own `name_hi` /
  `category_hi` fields from the backend data, shown when Hindi is active.

### 4.5 API client (`lib/api.ts`)

- Centralizes every backend call with full TypeScript request/response
  typing.
- A shared `handle()` helper specifically detects FastAPI's default
  `{"detail": "Not Found"}` 404 body and rewrites it into a clearer
  developer-facing message ("this backend endpoint doesn't exist yet —
  the running backend is likely out of date"), distinguishing a genuinely
  missing route from an empty/no-data result.
- Base URL defaults to `http://127.0.0.1:8000` (explicit IPv4 loopback,
  not `localhost`) — chosen specifically because this file's fetches also
  run server-side during SSR (e.g. from `layout.tsx`), where Node on
  Windows resolves `"localhost"` to IPv6 first and can hang waiting for a
  timeout against a backend that only binds IPv4.

## 5. Data model (seed JSON files)

| File | Contents |
|---|---|
| `treatments.json` | Treatment catalog: id, name (+ Hindi), category (+ Hindi), aliases, symptoms, typical duration, description |
| `cost_records.json` | Sample cost rows: treatment × city × state × hospital type × min/max/avg cost × sample size × source × data year |
| `national_reference.json` | Cited PM-JAY/CGHS national package rates, per treatment × hospital type, for the subset of treatments where a real verifiable figure exists |
| `hospitals.json` | Hospital directory: id, name, type, city/state, lat/lng, contact, treatments offered, empanelled schemes, rating |
| `schemes.json` | Government scheme catalog: id, name, eligibility rules, coverage details, application steps, official link |
| `users.json`, `sessions.json`, `reset_tokens.json` | Runtime-created, gitignored — never shipped with seed data |

**All seed figures are placeholder sample data**, clearly marked in each
record's `source` field — not yet replaced with sourced CGHS/PM-JAY/state
tariff data.

## 6. Known limitations / deliberate trade-offs

- **No real database yet** — everything is flat JSON files; fine for an
  MVP, not for concurrent-write safety or scale.
- **Sample cost data is placeholder**, not verified real-world figures.
- **Password-reset email enumeration**: since no email service is
  configured, the reset endpoint returns the reset token directly in the
  API response when the account exists (and `null` otherwise). The
  frontend only shows the "reset link" button when a token comes back,
  which means account existence is technically distinguishable from the
  response shape, despite the message text being identical either way.
  Acceptable for an MVP demo; would need a real email-sending step to
  close fully.
- **No ML/LLM layer yet** — cost estimation and eligibility are 100%
  rule-based by design at this phase; an explanation layer (Claude,
  strict JSON-schema validated so it can only explain, never alter, a
  number) and a trained regression model are both planned for later
  phases, not implemented yet.
- **History is local-only** — not synced to an account or backend, so it
  doesn't follow the user across devices.

## 7. Planned next phases (not yet built)

1. **Data foundation** — real CGHS/PM-JAY rate lists and empanelled
   hospital directories, backed by Postgres/Supabase.
2. **Modeling layer** — an XGBoost/LightGBM regression model once real
   `cost_records` volume justifies it, plus a Claude-based explanation
   layer with strict schema validation guaranteeing it can't introduce or
   alter any number.
3. **Differentiators** — Budget Mode UI toggle (backend already supports
   `budget_mode=true`), a map view, voice input, EMI/loan info depth, and
   further Treatment Comparison enhancements.
4. **Trust hardening** — gate the disclaimer behind an explicit "I
   understand" acknowledgment, and add a post-generation number-drift
   check once the Claude explanation layer exists.
